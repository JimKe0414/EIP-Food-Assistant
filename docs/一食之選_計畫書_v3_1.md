# 一食之選：智慧飲食系統　計畫書 v3

> 修訂重點（v3）：在 v2 基礎上加入 PWA 支援（離線快取、安裝提示、背景同步）與 RWD 桌面版佈局規格（斷點系統、雙欄 / 三欄版型、鍵盤操作）。

---

## 1　產品定位

以 **Nuxt 3 / Nitro、PostgreSQL 與 Docker Compose** 建置，提供餐食記錄、營養分析與飲食趨勢功能。UI 依上傳原型拆為：首頁、餐食記錄、午餐推薦、趨勢、個人資料五個頁面。

支援平台：行動裝置（iOS Safari / Android Chrome）、桌面瀏覽器（Chrome / Firefox / Edge / Safari），以及可安裝的 PWA。

功能邊界：餐食記錄、營養分析、飲食趨勢視覺化，**不提供**疾病診斷、處方或用藥建議。

## 3　RWD 響應式設計

### 3.1　斷點系統

| 名稱 | 範圍 | 主要裝置 |
|------|------|---------|
| `mobile` | < 640 px | 手機直向 |
| `tablet` | 640 – 1023 px | 手機橫向、平板 |
| `desktop` | 1024 – 1439 px | 筆電、桌面 |
| `wide` | ≥ 1440 px | 大螢幕顯示器 |

以 **mobile-first** 撰寫 CSS；上方斷點覆寫。

### 3.2　各頁面版型規則

#### 3.2.1　整體外框

- `mobile`：單欄，全寬，底部導覽列固定。
- `tablet`：單欄居中，最大寬度 680 px，保留行動版導覽列。
- `desktop`：**左側固定導覽列（240 px）+ 主內容區**；底部導覽列隱藏。
- `wide`：左側導覽列（240 px）+ 主內容區（最大寬度 900 px）+ 右側資訊側欄（280 px）。

```
desktop / wide 版型（示意）
┌──────────────┬────────────────────────┬─────────────┐
│  左側導覽列  │      主內容區           │  右側側欄   │
│   240 px     │   （彈性寬，max 900）   │   280 px    │
│              │                        │（wide 才顯示）│
└──────────────┴────────────────────────┴─────────────┘
```

#### 3.2.2　首頁

- `mobile`：垂直卡片堆疊，今日攝取環形圖置頂。
- `desktop`：左欄顯示今日摘要與快速記錄入口；右欄顯示近 7 日趨勢迷你圖。
- `wide`：右側側欄顯示今日目標達成率與 AI 提示。

#### 3.2.3　餐食記錄

- `mobile`：底部彈出 sheet（照片 / 語音 / 文字三種入口）。
- `desktop`：輸入區改為**右側固定面板**（440 px），候選清單佔主內容區。
- 語音輸入：`mobile` 使用裝置麥克風 API；`desktop` 同樣支援，但 UI 改為浮動視窗而非全螢幕覆蓋。
- 照片上傳：`desktop` 支援拖放（drag-and-drop）到上傳區，並接受貼上（`paste` 事件）。

#### 3.2.4　午餐推薦

- `mobile`：垂直卡片列表。
- `desktop`：三欄卡片格（每欄 280 px 起），每張卡片顯示完整營養資訊（不折疊）。

#### 3.2.5　趨勢

- `mobile`：圖表全寬，單一指標切換。
- `desktop`：雙欄並排（週熱量趨勢 + 營養素分佈），圖表高度 320 px。
- `wide`：三欄並排，加入體重趨勢圖。

#### 3.2.6　個人資料

- `mobile`：垂直表單，各欄位佔滿寬度。
- `desktop`：雙欄表單格，基本資料左欄、身體指標計算右欄，儲存按鈕固定於右下角。

### 3.3　導覽列（desktop 版）

左側固定導覽列（240 px）包含：

- 頂部：應用名稱 + AI 處理模式標示（地端 / 雲端）。
- 中段：五個頁面連結（含 icon + 文字標籤）。
- 底部：登入帳號資訊 + 登出按鈕。

導覽列在 `desktop` 以上永遠顯示，不可收合（Phase 1）。可收合功能列入 Phase 2。

### 3.4　鍵盤操作與無障礙

- 所有互動元素均可以 Tab 鍵聚焦，並有可見的 focus ring（`outline: 2px solid`）。
- 底部 Sheet（mobile）與右側面板（desktop）開啟時，焦點鎖定（focus trap）在面板內，`Escape` 鍵關閉。
- 圖表以 `aria-label` 描述摘要數值，不依賴顏色作為唯一資訊載體。
- 動畫遵守 `prefers-reduced-motion: reduce`，降為淡入淡出。

### 3.5　觸控與指標輸入

- 觸控目標最小尺寸：44 × 44 px（iOS HIG / WCAG 2.5.5）。
- `desktop` 下 hover 狀態必須存在（卡片、按鈕、導覽項目）。
- 拖放上傳僅在 `pointer: fine`（滑鼠 / 觸控板）時啟用，觸控裝置回退為選擇檔案。

### 4.3　Service Worker 快取策略

| 資源類型 | 策略 | 說明 |
|---------|------|------|
| App Shell（HTML、JS、CSS）| **Cache First** | 安裝時預快取；版本更新時整批替換 |
| 圖示、靜態資源 | **Cache First** | 長效快取，版本號控制失效 |
| `/api/meals`（讀取）| **Network First，快取 fallback** | 離線時顯示最後一次成功的資料 |
| `/api/recommend-lunch` | **Network Only** | 推薦需要即時 AI，不快取 |
| `/api/nutrients`（食品資料）| **Stale While Revalidate** | 先回傳舊資料，背景更新 |
| 第三方 CDN 資源 | **Cache First**（限白名單網域）| — |

預快取清單在建置時由 `@vite-pwa/nuxt` 自動從 Vite manifest 產生，不手動維護。

### 4.4　離線行為

| 狀況 | 行為 |
|------|------|
| 離線開啟 App | 顯示最後快取的首頁；頂部 banner 提示「目前離線，顯示最後同步資料」 |
| 離線記錄餐食（文字）| 寫入 IndexedDB 暫存，連線恢復後**背景同步**上傳（Background Sync API）|
| 離線記錄餐食（照片 / 語音）| 提示「照片與語音分析需要網路連線」，不暫存 |
| 離線請求午餐推薦 | 提示「推薦需要網路連線」，顯示上次推薦結果（唯讀）|
| 離線瀏覽趨勢 | 顯示快取資料，右上角顯示最後同步時間 |

### 4.5　背景同步（Background Sync）

離線餐食記錄（文字）流程：

```
1. 使用者提交 → 寫入 IndexedDB（pending_meals 表）
2. UI 顯示「已暫存，連線後自動上傳」
3. Service Worker 註冊 sync 事件（tag: 'sync-meals'）
4. 連線恢復 → Service Worker 讀取 pending_meals → POST /api/meals
5. 成功後從 IndexedDB 刪除；失敗則保留，下次重試（最多 3 次）
6. 同步完成後推送通知（若已取得通知權限）：「N 筆餐食記錄已同步」
```

不支援 Background Sync API 的瀏覽器（如 iOS Safari < 16.4）：退回為「連線恢復時前景自動重試」，使用者須保持頁面開啟。

### 4.6　安裝提示（Add to Home Screen）

- 偵測 `beforeinstallprompt` 事件（Chromium 系列）；iOS Safari 無此事件，改以 banner 顯示「點選分享 → 加入主畫面」引導說明。
- 首次開啟 App **3 天後**或使用者完成第 5 次餐食記錄後，才顯示安裝提示，避免過早打擾。
- 使用者拒絕後 **30 天**內不再提示。
- 已安裝（`display-mode: standalone`）則永遠隱藏提示。

### 4.7　推播通知（Phase 2，Phase 1 預留介面）

Phase 1 僅預留通知權限請求入口與資料庫欄位（`push_subscription`），不實作推播業務邏輯。Phase 2 才實作：

- 午餐推薦提醒（11:30，依使用者設定）
- 背景同步完成通知
- 每日飲食摘要（20:00，依使用者設定）

### 4.8　PWA 更新策略

- Service Worker 使用 `prompt` 更新模式：有新版本時在頁面底部顯示「有新版本，點此更新」Banner，使用者點擊後重新載入，不自動強制更新。
- 舊版 Service Worker 在所有分頁關閉後自動失效。

### 4.9　PWA 相容性說明

| 瀏覽器 | 安裝 | 離線 | Background Sync | 推播（Phase 2）|
|--------|------|------|-----------------|----------------|
| Chrome（Android / 桌面）| ✓ | ✓ | ✓ | ✓ |
| Edge（桌面）| ✓ | ✓ | ✓ | ✓ |
| Firefox（桌面）| ✗（無安裝）| ✓ | ✗ | ✓ |
| Safari（iOS 16.4+）| ✓（主畫面）| ✓ | ✗ | ✓（iOS 16.4+）|
| Safari（iOS < 16.4）| ✓（主畫面）| 部分 | ✗ | ✗ |

iOS Safari 的 IndexedDB 在 PWA standalone 模式下儲存空間有限（~50 MB），應避免快取大量照片。

## 5　AI Provider 層

### 5.1　AiProvider 介面（三個方法，統一 Zod schema 驗證）

```typescript
interface AiProvider {
  analyzeMeal(input: TextOrImage): Promise<MealAnalysisResult>
  transcribeMeal(audio: AudioBuffer): Promise<TranscriptionResult>
  recommendLunch(context: LunchContext): Promise<LunchRecommendation>
}
```

所有回傳值以 Zod schema 驗證；驗證失敗時拋出 `AiProviderError`，不讓未驗證資料進入業務邏輯。

### 5.2　支援的 Provider

| Provider | 文字 | 影像 | 音訊 |
|----------|------|------|------|
| `ollama` | ✓ | ✓（需支援視覺的模型）| ✗ |
| `local-whisper` | — | — | ✓（faster-whisper）|
| `openai-compatible` | ✓ | ✓ | ✓ |
| `google-genai` | ✓ | ✓ | ✓（需 File API 上傳）|

### 5.3　已驗證支援結構化輸出的 Ollama 模型

以下模型已確認支援 JSON mode（`format: "json"`）：

- `llama3.1:8b`、`llama3.1:70b`
- `mistral:7b`、`mistral-nemo`
- `llava:13b`（視覺）、`llava-llama3`（視覺）

**使用其他模型前，必須先執行 `scripts/verify-json-mode.sh <model>` 通過才可投入生產。**

### 5.4　Google Gemini 音訊處理流程

Gemini 音訊須先上傳 File API，流程如下，每步驟均須處理失敗：

```
1. POST /upload/v1beta/files          → 取得 file_uri
2. 輪詢 GET /v1beta/files/{name}      → 等待 state = ACTIVE（逾時 30 s）
3. 呼叫 generateContent（帶 file_uri）
4. 任務結束（成功/失敗/取消）後 DELETE /v1beta/files/{name}
```

步驟 4 必須在 `finally` 區塊執行，確保暫存檔無論如何都被清除。

## 6　GPU 資源排程策略

### 6.1　問題背景

Ollama 推論（視覺/文字）與 faster-whisper（語音）同機競用 GPU，無排程策略時會出現 OOM Kill 或互相等待。

### 6.2　解決方案：單 Worker Queue

- `worker` 容器以**單一 GPU worker** 串列處理所有 AI 任務（BullMQ / pg-boss）。
- 任務佇列優先順序：`analyzeMeal` > `transcribeMeal` > `recommendLunch`。
- 每個任務有**最大執行時間**（`analyzeMeal` 30 s，`transcribeMeal` 60 s，`recommendLunch` 20 s），逾時強制終止並回傳錯誤。
- faster-whisper 服務在有音訊任務時才載入模型，完成後釋放 VRAM（`--model-cache-enabled false`）。

### 6.3　GPU 記憶體需求（最低規格）

| 模式 | 最低 VRAM |
|------|-----------|
| 視覺模型（llava:13b）| 10 GB |
| 文字模型（llama3.1:8b）+ whisper medium | 8 GB |
| 文字模型（llama3.1:8b）| 6 GB |

低於最低規格時，啟動腳本應警告並拒絕以 GPU 模式執行。

### 6.4　Compose 配置

```yaml
# compose.gpu.yml（覆寫）
services:
  worker:
    deploy:
      resources:
        reservations:
          devices:
            - driver: nvidia
              count: 1
              capabilities: [gpu]
    environment:
      - GPU_CONCURRENCY=1   # 禁止平行 GPU 任務
```

## 7　資料模型與個人資料

個人資料保存：年齡、身高、體重、體脂率（選填）、活動量係數，建立量測快照（每次儲存均記錄時間戳記，不覆蓋舊值）。

計算項目：

| 指標 | 公式 | 前置條件 |
|------|------|---------|
| BMI | 體重(kg) / 身高(m)² | 必填 |
| IBW | 22 × 身高(m)² | 必填 |
| 脂肪重量 / LBM | 體重 × 體脂率 | 體脂率必填 |
| BMR（Katch-McArdle）| 370 + 21.6 × LBM | 體脂率必填 |
| BMR（Mifflin-St Jeor）| 10W + 6.25H − 5A ± 5 | 體脂率未填時回退 |
| TDEE | BMR × 活動量係數 | — |

> 體脂率為使用者自填數字，影響 BMR 計算精度。UI 應在體脂率未填時明確提示「使用估算 BMR，精度較低」，而非靜默回退。

## 8　餐食記錄流程

文字、語音、照片三種輸入皆先產生**候選清單**，經使用者確認或修正後才寫入正式餐食記錄、營養分析與摘要。

```
使用者輸入 → AI 分析 → 候選清單（顯示信心值）→ 使用者確認/修正 → 寫入 DB
```

原始照片與音訊只在 worker 容器暫存；任務完成、失敗或取消後立即刪除（Gemini File API 亦同，見 §5.4）。

### 9.2　XLSX 欄位結構

食藥署 XLSX 採「每 100 g 可食用部分」為計算基準。系統解析時使用以下欄位（欄名以資料庫新版為準）：

#### 必要欄位（缺少任一欄即拒絕整批更新）

| 欄名 | 說明 | 型別 |
|------|------|------|
| 樣品編號 | 唯一識別碼，格式如 `A0100101` | 字串 |
| 樣品名稱 | 食品中文名稱 | 字串 |
| 俗名 | 常見別名（可為空） | 字串 |
| 內容物描述 | 品項說明（可為空） | 字串 |
| 廢棄率（%）| 不可食用部分比例 | 數值 |
| 熱量（kcal）| 每 100 g 熱量 | 數值 |

### 9.3　正常同步流程

```
1. 每日 02:00 Asia/Taipei，worker 以 HEAD 請求確認 ETag / Last-Modified
2. 若與上次相同 → 記錄「無更新」，結束
3. 若不同（或首次）→ GET 下載 XLSX 到 worker 容器暫存路徑
4. 以 SHA-256 計算檔案雜湊，比對上次成功版本
5. 若雜湊相同 → 記錄「無更新」，刪除暫存檔，結束
6. 解析 XLSX（Sheet 1）→ 驗證必要欄位存在且型別正確
7. 以 DB 交易寫入 `nutrients_staging` 表（整批替換）
8. 驗證通過 → 交易切換 `nutrients` 正式版本，記錄版本快照
9. 刪除暫存檔；記錄同步成功、版本雜湊與筆數
```

> 步驟 3 的暫存檔無論成功或失敗都在流程結束時刪除（`finally`）。

### 9.4　降級策略（明確定義）

| 狀態 | 行為 |
|------|------|
| 下載失敗 / 欄位驗證失敗 | 保留上一個成功版本，寫入同步失敗日誌 |
| 上一個成功版本距今 **≤ 7 天** | 繼續正常服務，UI 無提示 |
| 上一個成功版本距今 **8–30 天** | 在推薦結果旁顯示「營養資料可能較舊（N 天前更新）」 |
| 上一個成功版本距今 **> 30 天** | 停用基於食藥署資料的推薦，並通知管理員 |

### 9.5　欄位映射版本控制

同步任務記錄所下載 XLSX 的欄位名稱清單雜湊（SHA-256）。若欄位異動（食藥署改版新增或移除欄位）則：

- 必要欄位缺少 → 同步失敗，發送告警，**不更新正式版本**。
- 新增未知欄位 → 發送告警（提示需更新欄位映射），**仍繼續同步**（以現有欄位為準，未知欄位忽略）。
- 欄位順序變動 → 以欄名比對，不依欄位位置解析，因此順序變動不影響正確性。

## 10　EIP 個人點餐匯入

### 10.1　授權模型

- 僅已登入使用者可上傳自己的 CSV/XLSX 匯出檔。
- 匯入任務自動綁定當前登入者的 HMAC 身分鍵（以 Workspace email 計算，不落庫）。
- 不接受使用者指定或覆寫他人身分。

### 10.2　EIP 匯出格式規格（Phase 1 接受格式）

解析器接受下列格式，**任何不符規格的檔案一律拒絕，不嘗試部分匯入**：

```
必要欄位（欄名不分大小寫，可含空白）：
  日期        格式：YYYY/MM/DD 或 YYYY-MM-DD
  餐點名稱    非空字串，長度 ≤ 100
  熱量(kcal)  正整數或正浮點數

選填欄位：
  蛋白質(g)、脂肪(g)、碳水化合物(g)、鈉(mg)

身分識別規則（多使用者偵測）：
  - 若同一檔案包含 2 個以上「不同 HMAC 簽章對應的 email」欄位值 → 拒絕
  - 若「使用者姓名」欄位出現超過 1 個不同的值 → 拒絕
  - 上述欄位若不存在則略過此檢查（單人匯出通常不含身分欄位）

檔案大小上限：10 MB
單次匯入筆數上限：5,000 筆（超過則拒絕，提示分批上傳）
```

### 10.3　資料隔離

EIP 個人點餐紀錄、使用者上傳菜單與自建餐點均為私有資料：

- Row-level security（PostgreSQL RLS）以 `user_id` 隔離。
- 所有查詢在應用層加上 `WHERE user_id = :currentUser` 且由 ORM 強制，禁止動態拼接。
- 其他登入者無法讀取、搜尋或將其用於推薦。

## 11　午餐推薦流程

AI 整合以下來源，依固定優先順序回傳候選：

```
1. 使用者上傳的當日 EIP 葷／素菜單（私有，限本人）
2. 使用者自主建檔餐點（私有，限本人）
3. 食藥署資料庫通用餐點（公開）
```

AI **只能回傳既有候選的 ID**，服務端在回傳前驗證：

- 候選 ID 存在於資料庫。
- 候選屬於當前登入者（私有資料）或公開食品資料。
- 驗證失敗的候選從結果中移除，不拋出錯誤（降級處理）。

### 11.1　Rate Limit

`POST /api/recommend-lunch` 限制：**每用戶每 5 分鐘最多 10 次請求**。超過後回傳 `429 Too Many Requests`，`Retry-After` 標頭指示剩餘等待秒數。

## 12　安全設計

### 12.1　HTTP 安全標頭（server/middleware/security.ts）

- 允許方法：`GET`、`POST`、`OPTIONS`；其餘一律 `405`。
- 拒絕含 `Transfer-Encoding` 的請求（HTTP request smuggling 防護）。
- 拒絕 URL 含 `..;` 的請求。
- 設定 CSP、HSTS、`Cache-Control: no-store`（API 回應）、Referrer-Policy、Permissions-Policy。
- 移除 `Server`、`X-Powered-By`（應用層）；CDN/反代層另行處理。

### 12.2　CSP Nonce（server/plugins/csp-nonce.ts）

- 每個 request 產生 nonce，注入 SSR 的 `<script>`、`<style>`。
- Development：保留 Nuxt/Vite HMR 所需的 `'unsafe-eval'`。
- Production：嚴格 CSP，無 `'unsafe-inline'`、無 `'unsafe-eval'`。
- PWA Service Worker 的 `scope` 路徑需加入 CSP `worker-src 'self'`。

### 12.3　CSRF

`GET /api/csrf-token` 實作 double-submit token；所有非 OAuth callback 的 `POST` 均須提交 cookie 與 `x-csrf-token` header，不符則 `403`。

### 12.4　Google SSO

OAuth state + PKCE + HttpOnly / Secure / SameSite=Strict session cookie，限制設定的 Workspace 網域。email 僅在當次登入或 EIP 匯入比對時用於計算 HMAC，**不保存至資料庫**。

### 12.5　API Key 管理

**禁止**以 `.env` 文件部署 API key 至生產環境。

- Docker Compose 生產部署：使用 `secrets:` 區塊，掛載至 `/run/secrets/`。
- Kubernetes：使用 `Secret` resource，以 `envFrom` 注入。
- Key 不得出現在 client bundle、日誌、錯誤訊息或 HTTP 回應中。
- CI pipeline 中以 mock provider 執行，不需真實 key。

## 14　測試計畫

### 14.1　單元測試

- 身體指標計算（BMI、IBW、BMR Katch-McArdle / Mifflin-St Jeor 回退邏輯）
- HMAC 匿名鍵（相同 email 產生相同 key；不同 email 不同 key）
- 食品比對（模糊比對、同義詞、單位換算）
- 三層推薦候選回退（EIP → 自建 → 食藥署）
- AI schema Zod 驗證（合法輸入通過；缺欄位、型別錯誤拒絕）
- TFDA 降級策略狀態機（7 天內 / 8–30 天 / 超過 30 天）

### 14.2　Provider Contract Tests

以**相同 fixture**驗證 ollama、openai-compatible、google-genai、local-whisper 回傳相同的 `MealAnalysisResult`、`TranscriptionResult`、`LunchRecommendation` 資料結構。

另以**邊界 fixture**驗證各 provider 的差異行為：

- Ollama JSON mode 失敗（模型不支援）→ 拋出 `AiProviderError`，不向上傳播裸字串
- Gemini File API 上傳失敗 → 暫存檔刪除、錯誤正確拋出
- openai-compatible 逾時 → 任務標記失敗、不掛起 worker

驗證 API key 不出現在 client bundle（`grep -r 'GOOGLE_GENAI_API_KEY\|OPENAI_COMPAT_API_KEY' .nuxt/` 應無結果）與日誌。

### 14.3　EIP 匯入測試

- 單一使用者合法檔案 → 成功匯入，資料綁定正確 `user_id`
- 多使用者欄位（2 個不同姓名）→ 拒絕，無任何資料寫入
- 超過 5,000 筆 → 拒絕，回傳明確錯誤訊息
- 其他使用者嘗試讀取匯入資料 → `404`（RLS 隱藏）
- HMAC key 覆寫攻擊（請求中帶入他人 user_id）→ 忽略，綁定登入者

### 14.4　整合測試（使用 stub，不依賴外部網路）

- TFDA XLSX 同步（均使用 WireMock / MSW stub，**不連外網**）：
  - 成功同步 → `nutrients` 表筆數正確、版本雜湊記錄

  - 欄位值為 `Tr` → `is_trace = true`，數值存為 `0.001`
  - 欄位值為 `—` / 空白 → 存為 `NULL`
